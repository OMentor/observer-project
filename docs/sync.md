# Синхронизация с внешними календарями

Версия: 1.2 (19.10.2026).
Область: Этап 6 MVP. CalDAV-провайдеры (Яндекс, Mail.ru). Apple iCloud отложен.
Связанные документы: `Проект.txt` §6.8, §12; `docs/api.md`; `docs/legal-sync-draft.md`.

---

## 1. Назначение и границы

Синхронизация позволяет пользователю связать источник внутри пространства
«Плетения» с календарём во внешнем сервисе и держать события в согласованном
состоянии в обе стороны.

**Границы ответственности**:

- «Плетение» — **обработчик** персональных данных. Владелец пространства —
  **оператор** (см. `legal-sync-draft.md`).
- Ответственность за сохранность данных на стороне провайдера (Яндекс,
  Mail.ru, Apple) лежит на провайдере. Мы не компенсируем потери, вызванные
  downtime, удалением или изменением формата на стороне провайдера.

**Вне scope MVP Этапа 6**:

- Google Calendar (Google Calendar API), Microsoft Outlook (Microsoft Graph) —
  отложены по причине недоступности консолей разработчика из РФ.
- Apple iCloud — отложен: нет iPhone/Mac у тестировщика для генерации
  app-specific password.
- Участники события (attendees), напоминания (VALARM), задачи (VTODO),
  вложения.
- Двустороннее редактирование сложных RRULE (см. §6).

## 2. Scope синхронизации

### 2.1. Что синхронизируется

| Сущность / поле | MVP | Позже |
|-----------------|-----|-------|
| Создание события локально → push во внешний | ✅ | — |
| Создание события во внешнем → pull к нам | ✅ | — |
| Изменение события (обе стороны) | ✅ | — |
| Удаление события (обе стороны) | ✅ | — |
| Поля: `title`, `description`, `start_at`, `end_at`, `all_day`, `location` | ✅ | — |
| Часовые пояса (IANA) | ✅ базово | ✅ полно (VTIMEZONE) |
| RRULE (повторения) | ✅ базовый (см. §6) | ✅ полный |
| Участники (`ATTENDEE`) | ❌ | ✅ |
| Напоминания (`VALARM`) | ❌ | ✅ |
| Задачи (`VTODO`) | ❌ | ✅ |
| Вложения (`ATTACH`) | ❌ | Никогда |
| Категории / теги (`CATEGORIES`) | ❌ | ✅ (маппинг на источники) |

### 2.2. Что не синхронизируется

- **Метаданные источника** (имя, цвет) — остаются локальными. Цвет источника
  в «Плетении» не перезаписывается цветом календаря провайдера.
- **Права доступа** — пресеты `FULL/OWN/BUSY/READ` работают только внутри
  «Плетения». Во внешнем календаре права определяются провайдером.
- **Участники пространства** — не становятся участниками внешнего календаря
  автоматически.

### 2.3. Направление синхронизации

По умолчанию — `both` (двустороннее). Пользователь при связывании может выбрать:

- `both` — чтение + запись (по умолчанию);
- `in` — только чтение из внешнего (полезно для «корпоративного календаря»,
  куда пишет только HR);
- `out` — только запись во внешний (полезно для «публичного календаря», который
  читают снаружи).

При `in` локальные события в источнике не пушатся; при `out` — внешние события
не подтягиваются.

## 3. Модель данных синхронизации

Полная схема — в `backend/prisma/schema.prisma`. Ключевые сущности:

### 3.1. `ExternalConnection`

Учётные данные и состояние подключения к провайдеру. Одна запись = одно
подключение пользователя к одному провайдеру.

| Поле | Назначение |
|------|------------|
| `userId` | Владелец подключения |
| `provider` | `yandex` / `mailru` / `apple` |
| `caldavUrl` | Базовый URL CalDAV |
| `caldavUsername` | Логин |
| `caldavPasswordEnc` | Пароль приложения, зашифрован AES-256-GCM |
| `syncToken` | Курсор синхронизации (WebDAV `sync-token`), если провайдер поддерживает |
| `lastSyncAt` | Время последней успешной синхронизации |
| `syncStatus` | `active` / `error` / `orphaned` |
| `lastError` | Текст последней ошибки (для UI) |

### 3.2. `SourceExternalMap`

Связь источника «Плетения» с календарём у провайдера. Один источник — один
внешний календарь (many-to-one не допускается).

| Поле | Назначение |
|------|------------|
| `sourceId` | Источник внутри пространства |
| `externalConnectionId` | Подключение |
| `externalCalendarId` | href календаря у провайдера |
| `externalCalendarName` | Имя для UI |
| `syncDirection` | `both` / `in` / `out` |
| `syncStatus` | `active` / `orphaned` |

### 3.3. `Event.external*` поля

| Поле | Назначение |
|------|------------|
| `externalId` | UID события у провайдера (`VEVENT.UID`) |
| `externalProvider` | `yandex` / `mailru` / `apple` |
| `externalEtag` | ETag для оптимистичной блокировки при push |
| `syncStatus` | `local` / `synced` / `pending` / `conflict` |
| `lastSyncedAt` | Время последней успешной синхронизации события |

### 3.4. `SyncConflict`

Неразрешённые конфликты. Создаётся, когда событие изменено с обеих сторон
в пределах окна (см. §4.2).

| Поле | Назначение |
|------|------------|
| `eventId` | Локальное событие |
| `externalConnectionId` | Подключение |
| `localData` | JSON: локальная версия полей |
| `externalData` | JSON: внешняя версия полей |
| `externalEtag` | ETag внешней версии на момент конфликта |
| `resolution` | `local` / `external` / `merged` / `null` |
| `resolvedAt` | Время разрешения |

## 4. Конфликты

### 4.1. Стратегия по умолчанию

**«Последнее изменение побеждает»** по `updated_at`, но с окном толерантности.

Причины:

- Ручное разрешение **каждого** конфликта — плохой UX для пользователя,
  который просто хочет, чтобы «всё работало».
- Auto-merge по времени корректен в 80–90% случаев (пользователь меняет
  событие в одном месте за раз).

### 4.2. Окно толерантности

**1 минута.** Если `|local.updated_at - external.last_modified| > 1 мин` —
auto-resolve по «последнее побеждает». Если в пределах 1 минуты — создать
`SyncConflict` и показать пользователю.

Обоснование: если обе стороны изменили событие с разницей >1 мин, это почти
наверняка разные действия (пользователь что-то поправил в одном месте, потом
в другом). Если в пределах 1 мин — вероятно, конфликт «одновременного
редактирования» (offline-изменения слились при подключении), и тут нужно
спросить.

### 4.3. Таблица правил

| Локально | Внешне | Условие | Действие |
|----------|--------|---------|----------|
| изменено | не изменено | `local.updated_at > external.last_synced` | Push локальной версии |
| не изменено | изменено | `external.last_modified > local.last_synced` | Pull внешней версии |
| изменено | изменено | `\|diff\| > 1 мин` | Auto-resolve по «последнее побеждает» + запись в `event_history` с `auto_resolved` |
| изменено | изменено | `\|diff\| ≤ 1 мин` | Создать `SyncConflict` |
| удалено | изменено | любое | `SyncConflict` (не автоудалять; вероятно, пользователь хочет сохранить) |
| изменено | удалено | любое | `SyncConflict` |
| удалено | удалено | любое | Soft-delete локально, пометить `synced` |
| удалено | не изменено | любое | Push удаления |
| не изменено | удалено | любое | Soft-delete локально |

### 4.4. UI конфликта (web и mobile)

**Модальное окно** с тремя кнопками:

1. **«Наша версия»** — оставить локальную, push во внешний календарь (перезапишет).
2. **«Внешняя версия»** — принять внешнюю, перезаписать локальную.
3. **«Объединить»** — показать построчный diff по полям, пользователь выбирает
   для каждого поля. Кнопка активна только если поля не конфликтуют полностью
   (например, разное `title` и разное `location` можно объединить; разное
   `start_at` — нельзя).

**Что показываем**:

```text
Конфликт: «Встреча с клиентом»
─────────────────────────────────────────
Поле        Наша версия         Внешняя версия
─────────────────────────────────────────
Название    Встреча с клиентом  Встреча с Аней
Время       15:00 – 16:00       15:30 – 16:30
Место       Офис                —
─────────────────────────────────────────
[Наша версия]  [Внешняя версия]  [Объединить]
```

Где появляется:

- **Web**: индикатор в шапке (SyncIndicator → расширить), список конфликтов в
  `/sync/conflicts`.
- **Mobile**: бейдж на иконке календаря, экран «Конфликты синхронизации» в
  профиле.

#### 4.4.1. API разрешения (Фаза 4)

| Метод | Endpoint | Назначение |
|-------|----------|------------|
| `GET` | `/sync/conflicts` | Неразрешённые конфликты пользователя (фильтры `space_id`, `event_id`, `connection_id`; пагинация `limit`/`offset`) |
| `GET` | `/sync/conflicts/:id` | Один конфликт с полными `local_data`/`external_data` |
| `POST` | `/sync/conflicts/:id/resolve` | Тело `{ resolution: 'local' \| 'external' \| 'merged', merged_data? }` |

Снимки полей — snake_case (`title`, `description`, `start_at`, `end_at`,
`all_day`, `timezone`, `location`, `rrule`), даты — ISO-строки.

| Ветка | Поля события | ETag | Запись наружу |
|-------|--------------|------|----------------|
| `local` | текущие локальные | новый ETag ответа | `forcePush` (безусловный PUT) |
| `external` | из `external_data` | `= conflict.external_etag` | нет |
| `merged` | `{ ...local_data, ...merged_data }` | новый ETag ответа | `forcePush` |

- `merged_data` — частичное объединение: незаданные поля берутся из локальной
  версии; `description`/`location` могут быть явно `null` (очистка).
- `external_data` заполняется **в момент конфликта** снимком внешней версии
  (best-effort pull). Если снимка нет — `resolve('external')` → `500`.
- Транзакция: `Event` и `SyncConflict` фиксируются вместе. `forcePush`
  выполняется **вне** транзакции: при ошибке (сеть/провайдер) → `503`, конфликт
  остаётся неразрешённым, событие не меняется.
- `forcePush` использует **безусловный PUT** (без `If-Match`): `If-Match: *`
  не поддержан (Radicale трактует `*` как обычный ETag → `412`); при
  отсутствии объекта он создаётся заново (`If-None-Match: *`).
- Новый конфликт рассылается как событие `sync.conflict` через Redis-шину
  (воркер → API → комната `user:<id>`), т.к. push выполняется в отдельном
  процессе-воркере без WebSocket-сервера.


### 4.5. Приоритет источников

Если пользователь связал несколько источников с одним внешним календарём —
это ошибка конфигурации. При попытке связать второй источник с тем же
`externalCalendarId` — возвращать `409 Conflict` с текстом «Этот календарь
уже связан с источником "X"».

## 5. Жизненный цикл

### 5.1. Первичное подключение

1. Пользователь нажимает «Подключить Яндекс».
2. Вводит логин + пароль приложения.
3. `POST /sync/connections` — проверка кредов (попытка `listCalendars`).
4. При успехе — credentials шифруются, сохраняются в `ExternalConnection`.
5. Пользователь видит список календарей провайдера.
6. Выбирает источник «Плетения» + календарь провайдера + направление.
7. `POST /sources/:id/link` — создаётся `SourceExternalMap`.
8. Запускается первичная синхронизация (вне очереди, синхронно для первого
   pull, чтобы пользователь сразу увидел результат).

### 5.2. Первичный pull

Правило: локальные события **не перезаписываются**, дедупликация — по ETag.

- Полная выборка календаря (`fetchCalendarObjects`); каждый объект парсится
  iCal-парсером (`parseIcalEvent`).
- Если `external_id` (UID) уже есть в этом источнике и `external_etag`
  совпадает — пропускаем (идемпотентность).
- Если ETag изменился — обновляем поля события (`sync_status='synced'`).
- Если события нет — создаём с `external_id`, `external_provider`,
  `external_etag`, `sync_status='synced'`.
- События с `external_id`, которых нет во внешнем ответе, помечаются
  удалёнными (`deleted_at`). Локальные (`external_id IS NULL`) не трогаются —
  будут запушены в push-цикле.

Причина: пользователь мог создать события в «Плетении» до подключения. Они
не должны «пропасть» только потому, что их нет в новом календаре.

> Реализация Фазы 2 (MVP): pull — **полная выборка**. Инкремент по `syncToken`
> (WebDAV `sync-collection`) отложен до Фазы 6: tsdav требует
> `collection.objectMultiGet`, а токен в схеме хранится на подключении, а не
> на календаре (§3.1). Идемпотентность обеспечивается сравнением ETag.

### 5.3. Отключение синхронизации

`DELETE /sync/connections/:id` (или `DELETE /sources/:id/link` для одного
источника):

- Credentials удаляются из БД (не soft-delete — hard delete).
- `SourceExternalMap` удаляется.
- События с `external_id != null` становятся локальными:
  `external_id = NULL`, `external_provider = NULL`, `sync_status = 'local'`.
- События не удаляются — пользователь мог на них рассчитывать.

### 5.4. Удаление внешнего календаря у провайдера

Провайдер вернул 404 на `externalCalendarId` при pull:

- `SourceExternalMap.syncStatus = 'orphaned'`.
- В UI источник помечается бейджем «Календарь недоступен».
- События остаются локальными (становятся `local`, как в §5.3).
- Пользователь может: переподключить (создать новую связь) или разорвать.

### 5.5. Смена провайдера

Пользователь был на Яндексе, переехал на Mail.ru:

1. Отключает Яндекс (§5.3) — события становятся `local`.
2. Подключает Mail.ru.
3. Связывает тот же источник с новым календарём.
4. Первичный pull создаёт новые события с новыми `external_id`.

В результате в источнике — дубликаты (старые `local` + новые `synced`).
Мы не мержим автоматически. Показываем в UI «Возможные дубликаты:
N событий», пользователь решает: удалить старые, оставить оба, объединить
вручную. Автомерж — отдельная задача, вне scope MVP.

### 5.6. Удаление источника «Плетения»

`DELETE /sources/:id`:

- Если есть `SourceExternalMap` — сначала разорвать связь (см. §5.3).
- Внешний календарь у провайдера **не удаляется** — только локальный источник.
- События источника — soft-delete локально.

### 5.7. Удаление пользователя

`DELETE /users/me`:

- Все `ExternalConnection` пользователя — hard-delete (credentials стёрты).
- Все `SourceExternalMap` — каскадно.
- Все `SyncConflict` — каскадно.
- Внешние календари у провайдеров не трогаются.

## 6. RRULE-политика (Вариант 1 — базовый)

### 6.1. Что поддерживаем при создании

| Правило | Поддержка |
|---------|-----------|
| `FREQ=DAILY` | ✅ |
| `FREQ=WEEKLY` (без BYDAY) | ✅ |
| `FREQ=WEEKLY;BYDAY=MO` (один день) | ✅ |
| `FREQ=MONTHLY;BYMONTHDAY=N` | ✅ |
| `FREQ=YEARLY` | ✅ |
| `INTERVAL>1` (каждый второй…) | ✅ |
| `COUNT` / `UNTIL` | ✅ |
| `BYDAY=MO,WE,FR` (несколько дней) | ⚠️ отображение read-only |
| `EXDATE` (исключения) | ⚠️ отображение read-only |
| `RECURRENCE-ID` (изменение одного вхождения) | ⚠️ отображение read-only |
| Комбинации `BYSETPOS`, `BYMONTH`, `BYYEARDAY` | ⚠️ отображение read-only |

### 6.2. Принцип «отображать умеем всё, создавать — только простое»

- **Pull**: любое валидное RRULE от провайдера сохраняется как есть (строка)
  и отображается в календаре (развёртывается для видимого диапазона).
- **Push**: если пользователь создал событие с правилом из «✅» — push
  соответствующего RRULE. Если правило сложное (из «⚠️») и пришло от
  провайдера — событие нельзя редактировать в «Плетении», только удалить
  серию.
- **UI**: если правило сложное — форма события показывает read-only блок
  «Повторение: каждый пн, ср, пт (изменено во внешнем календаре)» с кнопкой
  «Открыть во внешнем календаре» (ссылка на провайдера).

### 6.3. Редактирование серии

В MVP — только два сценария:

- «Вся серия» — изменение применяется ко всем вхождениям.
- «Отмена» — без изменений.

Сценарий «это и все будущие» — вне scope MVP, добавляется в Этапе 7 (полный
RRULE).

### 6.4. Развёртывание серии

Pull получает одно событие с RRULE. В локальной БД хранится одно
событие. При отображении в календаре — развёртывается в виртуальные экземпляры
для видимого диапазона (месяц/квартал).

Библиотека: `rrule` (npm). Для каждого вхождения — `recurrence_id`
(виртуальный, не хранится в БД). При клике на виртуальное вхождение — открывается
форма редактирования серии (см. §6.3).

## 7. Провайдеры

### 7.1. Яндекс

| Параметр | Значение |
|----------|----------|
| CalDAV URL | `https://caldav.yandex.ru` |
| Аутентификация | Basic, пароль приложения (создаётся в `passport.yandex.ru` → «Пароли приложений») |
| Поддержка sync-token | Частичная (WebDAV sync-collection) |
| Особенности | Ограничение на размер PROPFIND-ответа; рекомендуется `Depth: 1`; отправлять явный `User-Agent` (иначе возможен 403) |

### 7.2. Mail.ru

| Параметр | Значение |
|----------|----------|
| CalDAV URL | `https://calendar.mail.ru` |
| Аутентификация | Basic, пароль для внешних приложений |
| Поддержка sync-token | Есть |
| Особенности | Некоторые календари read-only (общие, корпоративные) — учитывать `current-user-privilege-set` |

### 7.3. Apple iCloud

| Параметр | Значение |
|----------|----------|
| CalDAV URL | `https://caldav.icloud.com` |
| Аутентификация | Basic, app-specific password (создаётся на `appleid.apple.com` с iPhone/Mac) |
| Поддержка sync-token | Есть |
| Особенности | Обязательно `User-Agent` в запросах; иначе — 403 |

Если у тестировщика нет iPhone — Apple откладывается, scope сокращается
до 2 провайдеров.

## 8. Синхронизационный цикл

### 8.1. Порядок

Для каждого активного `SourceExternalMap`:

1. **Pull**: получить изменения от провайдера с `syncToken` (или полный список
   при первом pull).
2. **Слияние**: применить §4 (конфликты, auto-resolve, создание `SyncConflict`).
3. **Push**: отправить локальные изменения (`syncStatus IN ('pending', 'local')`)
   во внешний календарь.
4. Обновить `lastSyncAt`, `syncToken`, `syncStatus` события.

### 8.2. Частота

- **Pull**: каждые 5 минут для активных подключений.
- **Push**: при изменении события — сразу (не ждём цикла), через воркер.
- **Force sync**: по запросу пользователя `POST /sync/connections/:id/force` —
  вне очереди.

### 8.3. Rate limiting

| Провайдер | Лимит | Стратегия |
|-----------|-------|-----------|
| Яндекс | ~1000 req/час на аккаунт | Батчинг, exponential backoff |
| Mail.ru | ~1000 req/час | То же |
| Apple | ~500 req/час | То же |

Retry: 3 попытки с задержкой 1 → 5 → 30 секунд. После 3 неудач —
`syncStatus = 'error'`, `lastError` заполнен. В UI — бейдж «Ошибка синхронизации».

## 9. Безопасность credentials

### 9.1. Шифрование

- Алгоритм: **AES-256-GCM**.
- Ключ: 32 байта, base64 в `ENCRYPTION_KEY` (в проде — Yandex KMS, локально — `.env`).
- IV: 12 байт, генерируется `randomBytes` на каждое шифрование.
- Формат хранения: `base64(iv || tag || ciphertext)`.

### 9.2. Ротация ключа

В MVP — не поддерживается. Потеря `ENCRYPTION_KEY` = потеря всех
credentials = пользователи должны переподключиться.

Действие: бэкап `ENCRYPTION_KEY` в защищённом хранилище (Vault, KMS),
вне репозитория.

В Этапе 7 — ротация через KMS с поддержкой двух ключей (старый для
расшифровки, новый для шифрования).

### 9.3. Логи

- Пароли, `caldavPasswordEnc`, `syncToken` **никогда** не логируются.
- При ошибке — логируется `provider`, `externalCalendarId`, `errorCode`, но
  **не** `errorMessage` (может содержать URL с credentials).

## 10. Ошибки и retry

| Код | Причина | Действие |
|-----|---------|----------|
| 401 | Неверные credentials | `syncStatus = 'error'`, `lastError = 'Требуется повторное подключение'`. UI: бейдж «Отключить» |
| 403 | Календарь read-only | Пропустить push для этого календаря, пометить в UI |
| 404 | Календарь удалён | `SourceExternalMap.syncStatus = 'orphaned'` |
| 429 | Rate limit | Exponential backoff (1 → 5 → 30 сек), 3 попытки |
| 500–504 | Ошибка провайдера | Retry с backoff, 3 попытки |
| Timeout (30 сек) | Сеть | Retry, 3 попытки |

- подключение → список календарей;
- создание события → push → проверка в веб-интерфейсе провайдера;
- создание события у провайдера → pull → проверка в «Плетении»;

### 11.4. Нагрузочное (вне MVP)

1000 событий в источнике, 4 месяца в QuarterView — pull + рендер < 2 сек.

  `POST /sync/connections/:id/force` (202, по одной задаче на `SourceExternalMap`).

  `app.get(PullService)` (не `@nestjs/bullmq`).

**Фаза 3 — детали:**
- `ical-serializer.ts` (`ical-generator`): VEVENT в UTC, `UID = external_id ?? id`,
  all-day → `VALUE=DATE`, `lastModified = updated_at`.
- `SyncProvider.push(calendarId, event)`: `etag === null` → создание
  (`If-None-Match: *`, имя `${uid}.ics`), иначе обновление (`If-Match: etag`,
  объект ищется по UID). Возвращает актуальный ETag (из заголовка ответа, при
  отсутствии — повторный PROPFIND). `delete(calendarId, uid)` находит объект по
  UID и удаляет; отсутствие — не ошибка.
- Конфликт: HTTP **412**/404 → `SyncConflictError` → `PushService` пишет
  `SyncConflict` (без дублей) и `Event.sync_status = 'conflict'`. Транзиентные
  ошибки пробрасываются для retry (3 попытки, backoff 5 → 10 → 20 сек).
- Триггеры: `EventsService.create/update/remove` ставят push-задачу
  (`SyncQueueService.enqueuePush`), если источник связан внешне и направление
  `both`/`out`. Задача выносится в отдельный `SyncQueueModule` (без циклов
  зависимостей между `EventsModule` и `SyncModule`).
- Проверено end-to-end на Radicale: create/update/delete отражаются во внешнем
  календаре; смоделированный конфликт (правка снаружи + локальная правка) →
  `SyncConflict`, внешний объект не перезаписан.
